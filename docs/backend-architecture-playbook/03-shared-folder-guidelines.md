# `src/shared`: що це і коли його доповнювати

## 1) Що таке `shared`

`src/shared` — це **шар повторно використовуваної інфраструктурної/технічної логіки**, яка потрібна в кількох модулях.

У поточному коді тут уже живуть:

- `services/`
  - `TokensService` (JWT)
  - `CookieService`
  - `EmailService`
  - `HashService`
- `decorators/`
  - `@Public`, `@User`, `@Roles`
- `guards/`
  - `AuthGuard`
- `response/`
  - `ResponseWrapper`
- `templates/`
  - шаблони email

Тобто `shared` = «крос-модульні технічні цеглинки».

## 2) Коли потрібно додавати щось у `shared`

Додавай у `shared`, якщо одночасно виконуються умови:

1. Код **використовується або очікується до використання** у 2+ модулях.
2. Код **не належить конкретному домену** (не тільки для `organization`, не тільки для `task`).
3. Код інфраструктурний/універсальний:
   - безпека,
   - транспортні утиліти,
   - крос-платформені helper-и,
   - стандартні обгортки відповіді.

Приклади, що доречно переносити в `shared`:

- універсальний сервіс роботи з файлами/URL,
- загальний pagination helper,
- спільні auth/permission decorators,
- уніфіковані response/exception mapper-и,
- інструменти для email/sms/push інтеграцій.

## 3) Коли НЕ потрібно переносити в `shared`

Не переносити, якщо:

- логіка **чітко доменна** (наприклад правила модерації review, специфічні стани task),
- код використовується лише в одному модулі,
- перенос погіршить читабельність і збільшить зв’язаність між фічами.

Правило:

> Якщо код описує бізнес-правила конкретної сутності — його місце у feature-модулі, а не в `shared`.

## 4) Коли переносити сервіс у `shared`

Перенесення виправдане, якщо сервіс:

- уже дублюється у двох місцях,
- має стабільний, невузький API,
- не тягне за собою доменні залежності конкретної фічі.

Перед переносом перевір:

- чи немає в сервісі імпортів із конкретного feature (`@modules/...` або `src/<feature>/...`),
- чи можна інжектити його через `SharedModule` без циклічних залежностей,
- чи після переносу інтерфейс сервісу залишиться універсальним.

## 5) Рекомендована класифікація для `shared`

- `shared/services` — технічні cross-cutting сервіси.
- `shared/decorators` — універсальні декоратори для HTTP/auth/meta.
- `shared/guards` — guard-и для кількох модулів.
- `shared/response` — стандартизація формату відповіді.
- `shared/templates` — reusable template-и (email, повідомлення).

## 6) Антипатерни для `shared`

1. **"God shared"**: складати туди все підряд «щоб було в одному місці».
2. Змішувати інфраструктуру з доменною логікою.
3. Робити `shared` залежним від конкретного модуля.
4. Переносити код у `shared` занадто рано (до появи повторного використання).

## 7) Проста матриця рішення

- Використання тільки в одному модулі → **залишити у модулі**.
- Використання в 2+ модулях і технічний характер → **переносити в `shared`**.
- Висока доменна специфіка навіть при 2+ використаннях → краще виділити окремий доменний модуль, а не `shared`.
